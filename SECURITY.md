# Security

Bridge AI runs AI agents on your computer and can type into their terminals, so security problems matter. Please report them privately, not in a public issue:

- **GitHub:** the repo's Security tab › Report a vulnerability.

Say what the problem is, how to reproduce it, and what someone could do with it. You'll get an answer within a week.

## Supported versions

Only the latest release gets security fixes. Bridge AI tells you when a newer version is out and updates when you say so, or, in the desktop app on a Mac or Windows, by itself while you're away unless you turn that off (Settings › About & Updates). Running `install.sh` (or `install.ps1` on Windows) again also updates it.

## How Bridge AI protects you

- The server listens on `127.0.0.1` only. From a browser, it answers only Bridge AI's own pages: a request from any other site, or from another port on this computer (a project's dev server, say), is turned away, and no other site can show Bridge AI in a frame.
- Every request needs Bridge AI's key, which is kept in `~/.bridge-ai/api-token`, readable only by you. Bridge AI's own programs (the `bridge-ai` command, the Chief of Staff's `bridge`, `bridge-ai mcp`) read it from there, and the desktop app gives it to its own windows. A browser on this computer is let in by a one-time link (View › Open in Browser in the app, or `bridge-ai open`), which leaves a cookie no web page's script can read and no other site's page or link carries. Other programs, and other accounts on the computer, get nothing.
- Your phone reaches your computer one of two ways:
  - **Your relay**, a small Cloudflare Worker on your own account. Everything between the phone and the computer is end-to-end encrypted, and the relay passes on bytes it can't read. A phone pairs with a one-time code from your computer, and you get a notification whenever a new device pairs. See [PRIVACY.md](PRIVACY.md) for what the relay keeps.
  - **Tailscale.** A phone gets in with the code in Settings › Account & Devices › Phone, a one-time link like the one a browser on the computer uses, and keeps the same cookie. Who Tailscale says is asking never lets anyone in by itself (any program on the computer can send the same), and a phone through Tailscale can't change what only the computer itself changes. Other people on your tailnet, or on a tailnet you share, are turned away.
- **Bridge AI as an MCP Server** (off until you turn it on, in Settings › Agents & Models › MCP Servers at the computer itself, never from another device; a backup doesn't carry it) lets apps on this computer that you add it to (Claude Code, Claude Desktop, Cursor, Codex) read your whiteboards, the Studio files in your Places and your meetings' summaries, and make new boards, files and tasks. A change to something that exists only waits in Needs You until you keep it, and sending work to an agent is off until you turn it on, then waits for your approval each time. Transcripts, agents' conversations, mail and calendar aren't offered at all. What it returns is marked as data, not instructions, and every call is listed in Settings › MCP Servers. What an app reads goes to the model that app uses.
- Your other computers link with a one-time code, or by asking. When one asks, you allow it on the other computer after checking that both show the same six digits. Each computer commits to a random number before it sees the other's, so a relay in between can't try keys until the digits match.
- API keys you add are stored in `~/.bridge-ai/secrets.json`. The `~/.bridge-ai` folder is readable only by you. Keys are never sent anywhere except to the provider they're for.
- Markdown and HTML from agents, files and meetings are cleaned before they're shown. HTML pages you preview run in a sandbox that can't reach the app.
- **Share Links** give someone outside your devices one file, folder, Studio document or app, through your relay, end-to-end encrypted, checked on your computer and nothing more (below).
- Installs and updates check each download against the release's `SHA256SUMS.txt`. Every release file also has a build attestation from GitHub Actions, so you can check where it was built:

  ```sh
  gh attestation verify Bridge-AI-mac-arm64.dmg --repo sahil1/bridge
  ```

- The Android app (`Bridge-AI-android.apk`) is signed with the project's release key, the same for every version. Android installs an update over it only when it's signed with that key, so an APK from anyone else can't replace yours.

- Usage stats and crash reports are on unless you turn them off (Settings › About & Updates, or **Turn off** on the card that says they're on; `DO_NOT_TRACK=1` or `BRIDGE_TELEMETRY=0` keeps them off; see [PRIVACY.md](PRIVACY.md#usage-stats-on-unless-you-turn-them-off)): weekly and daily counts in ranges, and crash reports with names, folders, emails and keys taken out, with no ID and nothing you typed.
- The outside requests Bridge AI makes itself are for what it shows you: the weather (Open-Meteo, with only the coordinates you picked), market prices and news headlines (Yahoo Finance, the Federal Reserve, and public news feeds), and a check on GitHub for a newer version (Settings › About & Updates turns it off). Unless you turn them off, also the usage stats, to `counts.boldbridge.ai`, and crash reports, to `crashes.boldbridge.ai` (both in `shared/telemetry-schema.json`). Your agents talk to their own providers with your own sign-ins.

## Remote access

Your paired phones and linked computers are trusted with this computer: they can start agents, read files and type into terminals here, as you can. Remove a device you don't trust in Settings › Account & Devices, or, with Remote Screen and Preview on, untick it in Which Devices May Connect (below).

Remote Screen and Preview (a Beta Feature, off until you turn it on) adds guardrails, each set at the computer itself, never from another device or through Tailscale. Turning the Beta Feature itself on or off is done there too:

- **Remote Access Password.** Asked before a device sees this computer's screen or one of the apps its agents serve (as pictures on a phone, or at an address of its own on another computer), and checked here. It's kept only as a salted scrypt hash at OWASP's recommended cost; an older hash is made again at that cost the next time the password is typed. Five wrong tries lock that device out for 15 minutes: each try is counted before it's checked, one is checked at a time, a device has at most two sessions waiting at the password, and a lockout is never ended early except by Unlock at the computer. Changing or removing the password ends every session.
- **Control** needs the password, and goes back to view-only after 10 minutes without input. Taking it back then asks for the password again.
- **Ask Here First.** Allow or Deny at the computer for each session, saying which device asks, what kind it is and how it's connected (directly, or through which of your computers). Allowed to view, a device that then takes control is asked about again; after control went idle, Allow is asked for again too.
- **Which Devices May Connect.** A device unticked here can't use this computer at all: no agents, terminals, files, copies, previews, page sessions or screen, and none of its notifications. That holds whether Remote Screen and Preview is on or off; with it off, the devices kept out are listed with Allow in Settings › Account & Devices › Computers. It's checked in one place, before every request and connection a device makes, so anything added later is covered too. All it's told is that this computer hasn't let it in, and where that's changed; it can still unpair itself. Unticking a device ends what it has open here at once: its terminals, sessions, copies and requests on their way. This computer itself is never turned away; a browser through Tailscale isn't this computer, and isn't a paired device in the list either (Use on your phone has its own switch). Once you set a password or Ask Here First, or untick a device, a phone or computer paired after that, or first seen through another of your computers, starts New: shown in Settings and in Needs You with Allow, it waits to be let in while Remote Screen and Preview is on. A device unticked here that unpairs itself doesn't take that away, and one that pairs again with the same key comes back kept out.
- **Through your other computers.** A device of another of your computers reaches this one through that computer, which checks its own list and lockout first and says which of its devices it's for. This computer then checks that computer, and that device as it comes through it: it's listed here as coming through that computer, to untick here too, and its lockout is kept for that computer and that device together. What that computer asks of this one for one of its devices (a rename, a copy, a preview, a meeting to mention) says which device too. What this computer tells that one about itself (its agents, what waits on you here) says which of that computer's devices it keeps out, and that computer shows those devices none of it; a computer not let in here forgets what this one last told it. A computer on an older Bridge AI, which can't say which of its devices a request is for, can't be used from its devices once a guardrail is set here, and they're told to update it; its own requests, as itself, go on. One from before that, which says nothing of its devices at all, can't have them told apart from it: Which Devices May Connect says so next to it, and to update it. A device paired with both computers is known here as the same device only when it paired with both using the same key; a phone's browser and the Android app keep a key for each computer, so the same phone can be listed here more than once. Settings offers to keep out the entries that may be the same device; untick such a phone each way it comes.
- A device asking is told only its own standing and the screens it may pick (behind a password or Ask Here First, the screens and their stills only once it's past them): never the record, what's on another session's screen, or the other devices. Your devices' notifications and cards of a session say which computer, which device and how it came, and for how long; their Stop and Block This Device only ever narrow who may connect, and a device is let back in only at the computer it was unticked on.
- **Previews.** Only a server one of your agents' terminals started counts as an app (never one started from the home folder or Bridge AI's data folder). An app never runs as a Bridge AI page: another computer shows it at an address of its own, and next to a phone's page it comes in a sandbox with no origin of its own. The page drawn off screen for a phone stays on its own app, and its redirects and frames can't reach anything else on the computer.

The password, control and Ask Here First cover seeing and controlling the screen and the apps. Which Devices May Connect covers everything a device does on the computer, with the Beta Feature on or off.

## Share Links

A Share Link lets someone outside your devices see one file, one folder (read-only), one Studio document (view-only, always its latest) or one app an agent's terminal serves (usable, buttons included), for an hour, a day or a week. You make it from Files, Studio or the Preview tab, on the computer or a paired device, and see and stop it in Settings › Sharing.

- **The link's secret** is in its fragment (`#s=…`), which browsers never send, so the relay never has it. The page the link opens reads it, takes it out of the address at once and keeps it only in memory, never in the browser's storage (the password too, when one is asked for), so a reload asks for the link again. That page and your computer each prove they hold the secret before anything else, and everything after is end-to-end encrypted with fresh keys, as a phone's link is. The relay sees the share's id (made from the secret, not the secret), sizes and times.
- **Addresses of its own.** A link's page is never at your phone's page's address. On Bridge AI's relay, each link's page has an address of its own, and what it shows is at another address of its own under a separate share domain (on the Public Suffix List): a different site from the page holding the secret, from your phone's page and from every other link. What's shown gets what it asks for only through that page, and only as what's shared, never one of that page's own questions; it loads nothing from another site (its scripts, pictures, styles, fonts, frames and requests come only from its own address), though a link in it can still take its own frame elsewhere, as on any page. A site's or an app's scripts run there and nowhere else. Until Bridge AI's relay has its share domain, it shares sites and apps no more than a relay of your own does.
- **On a relay of your own**, links open at a second Worker beside it (`<name>-share`, on your workers.dev subdomain, so the same site to a browser as your other Workers there). It has no separate address for what's shown, so nothing shown there runs scripts: a site (a folder with web pages in it) or an app is refused, saying why, and files, folders without web pages and Studio documents are shown with scripts off.
- **Who may open it** is checked on your computer, never the relay: the link alone, the link and a password (at least 8 characters, kept only as a salted scrypt hash; 5 wrong tries in a row lock that page out, and 20 from anyone within 15 minutes lock the link for 15 minutes, and your devices are told), or only the people you name, each proving their email with an 8-digit code first (10 minutes, 5 tries; an email gets 5 codes an hour and 10 a day, and a link sends 60 a day). The accounts service emails a code only to an email the link named, which your computer tells it when the link is made (kept there as a hash only it can make, until the link ends).
- **Before it's let in** (the password or code given), a page may ask only what the link needs to let it in, with nothing it sends held; on Bridge AI's relay it's a stranger until then, with a small allowance of its own that costs your account nothing. Once your computer has welcomed it (the link's secret proved both ways), it keeps its place at the relay, but only a few such pages are held on a link (6, and 2 from one address), apart from the 10 it lets in, and each is let go a while after its last try (a minute for a password, three for a code), saying so; pages that haven't been welcomed yet wait in a small room of their own, a few from any one address. After it's let in, pages viewing your links have an allowance of their own on Bridge AI's relay, apart from your phones': their own pace, and so much in the account's window and in a week, for all your links and for any one (Settings › Sharing says how much). One sending too much is let go.
- **Only what's shared.** A link's requests are answered by the share itself, never by Bridge AI's server: no `/api`, no pages or files of Bridge AI. A file link serves that file; a folder link serves only regular files inside it (never a pipe or a device), never a name starting with a dot, a link (symlink) leading out of it, Bridge AI's own folder or your keys', and nothing once the folder itself has been moved or replaced. A hard link inside a folder is the file it links to, so it's shared too: share folders whose contents you know. Nothing is ever written, and only an app is sent what a page sends. An app link reaches only that app's port, only while an agent's terminal still serves it, never Bridge AI's own ports, with no cookies or Authorization passed on either way.
- **Contained.** What a link shows is sandboxed and can't reach the page holding the link, nor take that tab anywhere. In some browsers (Safari) a site or app shown can still send the tab back through its history without a click; the link's page keeps an entry of its own on top and stays where it is, though a page reached that way is no worse than the browser's Back button. A Studio document is shown as a page made on your computer with nothing in it that runs.
- **Your devices.** Which Devices May Connect covers Sharing: a device kept out sees no links and stops none. A link itself (its secret) is shown only on the computer and on the device that made it; your other devices see what each link shows, who opened it, and Stop Sharing.
- **Stop Sharing** (or the link's time running out) ends every open page at once, saying so, and forgets the link's secret, so nothing opens it again.
- **Limits:** 50 links at once, each open on 10 devices at once, files up to 1 GB, 8 answers on their way to a page at once (32 for a link), and a page asking more than about 40 times a second is slowed; an answer not read for 30 seconds is let go. Your devices hear of each link's first open.

The page a link opens comes from the relay, as your phone's page in a browser does, so whoever runs the relay could serve a page that reads the link: you trust the relay with your links as you do with your phone's page. On Bridge AI's relay, your computer checks the page it serves against the released one, as it does the phone's page.

What a link shows, whoever has the link can show to others: share a password or a named link for anything private, and stop it when it's done.

## Signing in Studio

- **Saved signatures and initials** are kept only on the computer, each one and their list encrypted (AES-256-GCM, each file bound to its name) with a key the desktop app makes and keeps in the computer's keychain through Electron's safeStorage (the Mac's login Keychain, DPAPI on Windows, a Linux secret service). The app hands the key to the server it starts on a pipe of its own, never in the environment, a file or a helper anyone can run; no copy of it is in the data folder. A server started another way (`npm start`, the CLI, Docker) keeps a key file readable by you alone, and Settings › Studio says so; the app seals them again with its own key the first time it starts that server, and never after: once the app has sealed the list, a key file put beside it is moved aside unused, and a list sealed with it is set aside, not taken as yours. When the app can't open its own keychain item (the prompt denied, or the item damaged), it never writes a new one over it: that run has no signatures' key, Settings › Studio says so, and the next run tries the item again. Still not opening then, Settings › Studio offers Start Over, after Touch ID, the Mac's password or Windows Hello: the old item is kept, a new key made, and the signatures sealed with the old one are set aside. No picture of one is kept in the open; one kept open by an older version is encrypted when Bridge AI starts and its open file overwritten and removed. A list this computer's key doesn't open is set aside, never deleted, and put back when a key that opens it is used again.
- **What that encryption protects against:** a copy of Bridge AI's data folder read anywhere else, such as a backup made by other software, a synced or copied folder, or a disk read without your login (the keychain isn't in the copy). It doesn't protect against everything running as you while you're logged in; see below.
- **Who can use them.** Their pictures, signing, every change to them, the trackpad, Sign on Phone, Ask Before Signing's setting and the PIN are only for the Bridge AI app's own windows on this computer and your phones (paired with this computer, kept, and let in by Which Devices May Connect). The app makes a window secret, keeps it with safeStorage and gives it to the server on the same pipe; its windows' requests to the server each carry a MAC of it, over the request's method, the address and port it's sent to, its path, its body's SHA-256 and the time, added by the app outside the page, so no page script has it, and one seen can't be used again, for another request, with another body or through another program passing it on. A server the app starts listens only at the address and port the app talks to it at (127.0.0.1), whatever its config says. Before it sends any, the app checks the server is the one it started, over that very connection (the server proves it has a secret given for that start only, naming both ends of the connection as the app sees them); a server that isn't gets nothing from the app's windows and its page isn't shown, and one of the app's own is started again. In the built app nothing goes to the server's address (its port, and each linked computer's) or comes from it until it has proved that: not a page (a window opening, a reload, after a crash, a popout, a device's window, the floating card, the capture window, dictation's), not a script, a request or a WebSocket (a terminal), not a message from a page there to the app, not a permission (the microphone, a screen) for one, not what its feed says, and not the app's own key; each page waits for the server to prove itself again first, and a window other than the main one opens its page again once it has. A proof not answered in time (a busy start, a Mac waking up) is tried again for about 15 seconds and shown as Bridge AI starting, never as another program, and never stops the server the app started; only a wrong answer counts as another program's. A server of the app's that ends by itself is started again (three times in five minutes at most), and checked as at the start. The window's MAC relies on the server's address (127.0.0.1 and its port) being its alone: two programs can't listen there at once, so the address a request was sent to is the server it reached. So 127.0.0.1 is the only address a page of the app's is at: localhost, [::1] and the other names for this computer at the app's ports are refused outright, as another program can listen there while the server does. A frame in a window (a project's app in Preview, which is sandboxed without top navigation, another computer's page) can't move the window, and a redirect out of the app opens in its own app instead. A service worker an older version left in the app's windows is removed when it starts (the app's page uses none). A new window secret is taken only with the signatures' own key, and Settings › Studio says when it changed. Bridge AI's key alone isn't enough (the CLI, `bridge-ai mcp`, a script, or a bot or agent with a shell), nor is the windows' cookie, which is made from that key. Nor is a browser tab (it says signing is done in the app), a device paired but not kept yet, or another of your computers. Signatures aren't among Bridge AI's MCP tools, a bot's files or a Share Link's (which never reach `/api`), are never sent to a model, and aren't in crash reports.
- **The Mac app** runs with Electron's fuses set so that Node.js's own options (`NODE_OPTIONS`) and its inspector (`--inspect`) can't be given to it, starts its server so that SIGUSR1 doesn't open Node's inspector in it either (`--disable-sigusr1`; Windows has its own way to ask a Node process to open it, `process._debugProcess`, which hasn't been checked there), and runs under the hardened runtime when it's signed with a certificate, so no other library is slipped into it (`DYLD_` variables) and no debugger attaches. Its signing helper (`native/bridgesign`) holds no key; it asks for Touch ID only for a program signed with the same certificate as itself (Bridge AI), checked by code signature.
- **Started only as it was built.** The built app (on a Mac, Windows or Linux) doesn't start when it's given Chromium's DevTools switches (`--remote-debugging-port`, `--remote-debugging-pipe`, `--remote-allow-origins`), Node's inspector (`--inspect` and its kin, which the fuses turn off too) or Chromium's stand-in for the keychain (`--use-mock-keychain`, which seals with a key everyone knows): it quits before any window, profile or key, and says why in `logs/desktop.log` in the data folder. Only a build made for the smoke test of the app's windows is let start with them, by a mark set as it's built inside the app's own archive, within its signature; no release build has it, and the release smoke test checks that and that each switch is refused. What's left: on Windows, the way another program can ask a running Node process to open its inspector (`process._debugProcess`) hasn't been checked against the app's server; and a program running as you can still use what you've allowed it on this computer (Accessibility, Screen Recording) to see or work the app's windows.
- **Back Up & Move** carries them only when ticked, from the app's window or your phone, and only after Touch ID, the Mac's password or Windows Hello (where the computer has none of these, the signing PIN if one is set). They go inside its sealed file or the encrypted link, and the other computer encrypts them again with its own key. Signatures added from a backup or a move are a change like any other: from your window or phone, asked first while Ask Before Signing is on.
- **Ask Before Signing** (off until you turn it on) is checked on the computer: Touch ID or the Mac's password through macOS LocalAuthentication (the helper the server runs, not the page; what it's for is written by the server from the document's name), Windows Hello, or a signing PIN. The server then gives a grant for that one document as it was when you confirmed (its SHA-256, which should match what the page showed you), used once, by the device that asked, within 2 minutes; a signed copy is made only from those same bytes, so a document changed after you confirmed is never signed, and making a signed copy without a grant is refused, whoever calls. While it's on, adding, replacing, removing or picking the default signature needs the same. The way this computer asks (Touch ID, the Mac's password or Windows Hello) is kept when it's turned on, from the computer or a phone: if the helper doesn't answer, signing waits and asks again rather than taking the PIN. Setting or changing the PIN and turning the setting off need the same confirmation. If the encrypted list can't be opened while the setting is on (a mark kept outside it says it was), or it's older than the app last saw, or says the setting is off when the app last saw it on (a copy put back: the app keeps the list's version and whether the setting was on in its keychain item), signing asks first until you confirm.
- **The signing PIN** (for your phone, or this computer where there's no other way) is kept as a salted scrypt hash with the signatures. Tries are checked one at a time, each counted before it's checked, so tries sent at once are tries one after another. After a wrong one the next waits a little (twice as long each time), and 5 wrong tries lock it for 5 minutes, twice as long each time after.
- **Sign on Phone** asks only your phones as above, checked when it's asked and when it's answered, never the device that asked. The relay proves which device each request is for with a secret the server keeps only in memory, so a request that only names a phone isn't taken for it. Each request has a random id and nonce and a key only the pad that asked has, without which it can't be followed or cancelled. It shows the same 4-digit code on the computer and the phone, ends after 2 minutes or when cancelled on either side, and takes one answer; another is refused. A few may wait at once, with a few notifications a minute, each asker (your window, each phone) its own. What comes back is strokes, drawn on the computer's pad, never kept until you keep them.
- **The trackpad** is read only while the pad in the app's window is listening, by the helper over its own window; the words it shows are the server's, in your language.
- **The record.** Each signing is kept in the document's versions on the computer: which way it was signed (the app's window or which phone), how it was confirmed, the places, the time and the SHA-256 of the original and of the signed copy, with a MAC made with the signatures' key over all of it and the two files it's about, so a record changed outside Bridge AI, or copied into another file's history, is shown as one that can't be trusted, and a signed copy changed since is said. The signed copy itself is never copied into Bridge AI's data folder, wherever it's moved: it's known by its hash and by a mark in its own information.

## What it doesn't protect against

- **Other accounts on the same computer, as an administrator.** Someone who can read your files (an administrator of the computer) can read Bridge AI's key too. Don't run Bridge AI on a computer you share with people you don't trust.
- **Anything already running as you.** Other apps and scripts you run can read your files, Bridge AI's key among them, and do whatever that key allows. They can't use your saved signatures through Bridge AI (above), but they can see your screen as you sign. On Windows and Linux they can also read the app's keychain item, and so the signatures' key. On a Mac signed with Bridge AI's own certificate, they can run the app's own code as Node.js and load a library of their own into it, which can read that item too (that certificate has no Apple team, so the app has to load libraries signed by anyone); a Developer ID build doesn't load such a library. With Ask Before Signing on, a signed copy made in Bridge AI still waits for Touch ID, the Mac's password or Windows Hello (or the signing PIN, where that's the way). Bridge AI run from its source code (`npm run desktop:dev`) takes the first window secret its app gives it, and keeps the signatures' key in a file.
- **A linked device you don't trust.** Linked phones and computers can do what you can, until they're unticked or removed: start agents, read files, type into terminals. In the desktop app or a browser on this computer, a linked computer's own pages open at a port of their own, so they can't reach this computer's page, what the app can do here (pictures of the screen, pasting, the microphone) or its settings; through a phone, Tailscale or another name for this computer they still open under its address. Link only devices you own, and remove any you no longer use in Settings › Devices.
- **Your agents themselves.** They run with your permissions and do what you (and the permissions you give them) allow.
- **A server swapped in between two proofs.** Once the server has proved itself, the app's windows' requests go to its address until its feed ends (the server stopping), when the next one waits for a proof again; each response isn't proved one by one. Another program could only answer at that address in the moment after the server has stopped and before the feed's end is seen, as two programs can't listen there at once.
- **The Mac app's signature.** Releases are signed with a Developer ID and notarized by Apple. A build signed with Bridge AI's own certificate (`node scripts/signing.js`, for building it yourself) isn't one macOS vouches for, and one signed ad hoc has no hardened runtime. Check the checksum or the attestation above if you download it yourself.
